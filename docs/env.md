# משתני סביבה, ומדריך יצירת פרויקט Supabase

## נוהל יומי, בדיקה על מכשיר אנדרואיד אמיתי

לבצע בדיוק בסדר הזה, **ולוודא כל שלב לפני שעוברים לבא**. רוב השגיאות החוזרות נובעות מדילוג על שלב האימות, לא מהפקודה עצמה.

**1. Supabase המקומי, מתוך `backend`.**

```bash
cd backend
```

```bash
npx supabase start
```

לוודא שהפלט מציג את הטבלה עם Project URL ולא שגיאת דוקר. אם דוקר לא היה פתוח, לפתוח אותו קודם ולחכות שיעלה במלואו לפני שמריצים את הפקודה הזאת.

**2. לחבר את הטלפון בכבל USB**, ולוודא שהמחשב מזהה אותו. מתוך תיקיית ה-adb מהשלב הבא:

```bash
.\adb devices
```

חייבת להופיע שורה עם המזהה של המכשיר ו-`device` לידה, לא `unauthorized` ולא רשימה ריקה. אם המכשיר לא מופיע, לנתק ולחבר את הכבל מחדש ולאשר את חלונית ה-USB Debugging בטלפון.

**3. להקים את שני הגשרים, ולוודא שהם תפסו:**

`adb` לא רשום ב-PATH של Windows אצל רון, ולכן קודם נכנסים לתיקייה שבה הוא יושב, ורק אז מריצים אותו בלי נתיב:

```bash
cd C:\Users\ronba\Downloads\platform-tools-latest-windows\platform-tools
```

```bash
.\adb reverse tcp:54321 tcp:54321
```

```bash
.\adb reverse tcp:8081 tcp:8081
```

```bash
.\adb reverse --list
```

PowerShell לא מריץ קובץ מהתיקייה הנוכחית בלי `.\` לפניו, זו התנהגות ברירת מחדל של PowerShell ולא קשורה ל-adb עצמו.

הפקודה השנייה חייבת להחזיר את שתי המיפויים. אם היא ריקה, השלב הזה נכשל בשקט ושום דבר אחרי זה לא יעבוד. **זו בדיוק הבדיקה שהייתה חסרה עד עכשיו** — הגשר נופל לפעמים לבד בין הרצת הפקודה לפתיחת האפליקציה, בלי שום הודעת שגיאה באותו רגע, והתקלה מופיעה רק כמה דקות אחר כך בזרימת ההתחברות.

**4. Metro, מתוך `frontend/mobile`, בטרמינל חדש:**

```bash
cd frontend/mobile
```

```bash
npx expo start --localhost
```

הוסיפו חבילה חדשה מאתמול? להריץ עם `--clear` בסוף במקום בלי.

**5. רק עכשיו לפתוח את Expo Go ולסרוק.** אם באמצע העבודה הטלפון מתנתק מהכבל ומתחבר מחדש בכל שלב, לחזור לשלב 3 ולהריץ שוב את שני ה-`.\adb reverse`, הם לא שורדים ניתוק.

**6. אם עובדים גם על הווב באותו יום, בטרמינל נוסף:**

```bash
cd frontend/web
```

```bash
npm run dev
```

אם עובדים רק על הנייד היום, אפשר לדלג על השלב הזה לגמרי.

אם משהו נכשל, הסדר לאבחון הוא תמיד מלמעלה למטה: קודם `.\adb devices`, אחר כך `.\adb reverse --list`, ורק אז לחשוד ב-Supabase או ב-Metro עצמם.

אם `adb` לא נמצא, הוא לא בהכרח ב-PATH של Windows. לבדוק עם `where.exe adb` בפאוורשל. אם זה לא מחזיר נתיב, להריץ עם הנתיב המלא, למשל `C:\Users\ronba\Downloads\platform-tools-latest-windows\platform-tools\adb.exe`, או להוסיף את התיקייה הזאת ל-PATH פעם אחת.

מסמך זה מסביר איזה משתנה סביבה שייך לאיזו אפליקציה, ואיך יוצרים את פרויקט ה-Supabase שכל שלושת הלקוחות מתחברים אליו. שום קובץ `.env` לא נכנס ל-git, רק קבצי `.env.example` נכנסים כתבנית.

## איך יוצרים פרויקט Supabase חדש

1. נרשמים ב-supabase.com עם חשבון גוגל או אימייל, בחינם.
2. לוחצים "New project", בוחרים שם, סיסמת מסד נתונים חזקה (שומרים אותה במקום בטוח, לא בצ'אט ולא ב-git), ואזור קרוב, בדרך כלל אירופה.
3. אחרי שהפרויקט נוצר, בתפריט Settings, יש שני מפתחות חשובים תחת API, ה-Project URL, וה-anon public key. אלה לא סודיים לחלוטין, אבל גם לא נכנסים בגלוי לקוד, תמיד דרך משתני סביבה.
4. יש גם service_role key, זה סודי לגמרי, משמש רק את ה-Worker בצד שרת, אף פעם לא בקליינט של הנייד או הווב.
5. מתקינים את Supabase CLI במחשב, כדי לנהל מיגרציות סכמה ולהריץ מסד מקומי לפיתוח. ההתקנה משתנה לפי מערכת הפעלה, יש הוראות מפורטות באתר של Supabase.
6. מריצים `supabase link` מתוך תיקיית השורש של הפרויקט כדי לחבר את `backend/supabase/migrations` הקיים בריפו לפרויקט האמיתי שנוצר.

אחרי שיש לך Project URL, anon key, ו-service_role key, תעביר אותם ואני אמלא את קבצי ה-`.env` המקומיים בהתאם, הם לא נשמרים ב-git בשום מקרה.

## אילו משתנים שייכים לאיזו אפליקציה

**`frontend/mobile/.env`**

`EXPO_PUBLIC_SUPABASE_URL`, כתובת הפרויקט.

`EXPO_PUBLIC_SUPABASE_ANON_KEY`, המפתח הציבורי, מותר להיות בקליינט כי RLS מגן על הנתונים בפועל.

`EXPO_PUBLIC_WORKER_URL`, כתובת ה-Cloudflare Worker, לקריאות קול, חילוץ, ו-OCR.

**`frontend/web/.env`**

אותם שלושה משתנים כמו בנייד, עם קידומת `VITE_` במקום `EXPO_PUBLIC_`, כי כך Vite חושף משתני סביבה ללקוח.

`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_WORKER_URL`.

**`backend/worker/.env` (מקומי לפיתוח), ובפרודקשן דרך `wrangler secret put`**

`SUPABASE_URL`, כתובת הפרויקט.

`SUPABASE_SERVICE_ROLE_KEY`, המפתח הסודי, אף פעם לא נחשף ללקוח, רק ל-Worker.

`OPENROUTER_API_KEY`, מפתח לקריאות תמלול, חילוץ JSON, ו-OCR מול OpenRouter.

`REVENUECAT_WEBHOOK_SECRET`, לאימות שהקריאה שמעדכנת entitlement במסד באמת הגיעה מ-RevenueCat.

## למה הנוהל הזה נראה כמו שהוא, הרקע שמאחורי השלבים

השלבים למעלה הם מה שעושים. זה למה, ומה לעשות כשמשהו בכל זאת משתנה.

**למה `supabase` חייב לרוץ מתוך `backend`.** ה-CLI מחפש `supabase/config.toml` יחסית לתיקייה שממנה הוא רץ. משורש הפרויקט הוא לא מוצא את `backend/supabase/config.toml`, ואז הוא מרים את הכל עם ברירות מחדל **בלי להגיד מילה ובלי שגיאה**. התוצאה נראית כמו הצלחה מלאה, אבל בפועל רשימת כתובות החזרה מאופסת וספקי הכניסה של גוגל ואפל כבויים. לאימות:

```bash
docker exec supabase_auth_yevul env | findstr URI_ALLOW_LIST
```

הרשימה חייבת להכיל את `localhost:5173`. אם היא מחזירה `127.0.0.1:3000`, ה-CLI רץ מהתיקייה הלא נכונה.

**למה Metro חייב לרוץ עם `--localhost`.** ב-Expo Go הפונקציה `Linking.createURL` מחזירה כתובת `exp://` ולא `yevul://`, כי הסכמה `yevul` רשומה במערכת ההפעלה רק לבילד משלנו. בלי `--localhost` הכתובת מכילה את כתובת ה-IP של המחשב ברשת, שמשתנה מדי פעם, ואי אפשר לרשום אותה מראש ברשימת ההיתרים של Supabase. תבנית כללית לא פותרת את זה, כי התבניות של Supabase לא חוצות נקודות ולוכסנים, נבדק בפועל מול השרת: `exp://**` אכן מתאים ל-`exp://abc` אבל לא ל-`exp://192.168.1.104:8081/--/`.

**מאיפה לוקחים את כתובת החזרה אם היא משתנה.** היא נגזרת מהשדה `hostUri` שהמניפסט של Expo מפרסם, ולא ממה שכתוב בטרמינל:

```bash
curl -s -H "expo-platform: android" http://127.0.0.1:8081/ | grep -o '"hostUri":"[^"]*"'
```

בגרסה הנוכחית הוא מחזיר `127.0.0.1:8081`, ולכן כתובת החזרה היא `exp://127.0.0.1:8081/--/`. גרסאות אחרות מפרסמות `localhost:8081`, ולכן שתי הצורות רשומות ב-`config.toml`. אם הבדיקה מחזירה משהו שלישי, זו הכתובת שצריך להוסיף.

**גבול תוקף.** כל זה נכון ל-Expo Go בלבד. ברגע שעוברים ל-development build, הסכמה `yevul://` עובדת כרגיל וההיתר של `exp` מיותר. **את ההיתר הזה אין להעביר לרשימת ההיתרים של פרודקשן.**

## עקרון כללי

מפתח סודי אמיתי, service role, מפתחות AI, סודות webhook, יושב אך ורק ב-Worker, אף פעם לא בקליינט של נייד או ווב, גם לא כמשתנה סביבה מקומי לבדיקות ארוכות טווח. מפתח שמותר בקליינט, anon key, מוגן על ידי RLS ולא על ידי הסתרתו.
